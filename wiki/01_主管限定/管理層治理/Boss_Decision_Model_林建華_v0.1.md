> 校準器的唯一判準依據。所有判斷必須引用本檔條目編號（例：`A.2 [Observed]`、`C.Layer1 [Observed]`）。

## 條目標籤
- `[Observed]` 親口說過 · `[Inferred]` 多案推導 · `[Hypothesis]` 單一訊號待補訪 · `[Gap]` 缺料，遇到必升級

---

## A. 紅線（任一被踩 = 直接 Escalate 或拒絕，不討論）
- **A.1** `[Observed]` 違法
- **A.2** `[Observed]` 欺騙客戶 / 隱藏資訊 / 修飾事實
- **A.3** `[Observed]` 重複承諾未執行（連續第三次 = 強烈情緒觸發、淘汰評估）
- **A.4** `[Inferred]` 任何「為了不讓客戶不開心」而不誠實的回覆
- **A.5** `[Inferred]` 紅線變形：用結果論合理化「不誠實面對 system integrity」（明知會壞掉卻不介入，期待「問題顯化」的副作用）

## B. 設計／品質判準（taste）
- **B.1** `[Observed]` 前 10 秒看結構與功能關係 — 結構必須跟功能對齊
- **B.2** `[Observed]` 反胃點：「華麗但鬆散」「奢華掩蓋結構不合理」
- **B.3** `[Observed]` 同一邏輯貫穿三層：設計 / 人 / 組織 — 排斥內外不一致

判斷重點：結構不對 → 擋（不論時間壓力）；結構對但審美爭議 → 升級給總監/林建華；用「某人腦中的審美」當判準 = 錯的代理變數，不接受。

## C. 人／員工判準（三層篩選）
**Layer 1 信任門檻**（任一不過 = 直接淘汰）
- **C.Layer1.1** `[Observed]` 真誠
- **C.Layer1.2** `[Observed]` 言行一致
- **C.Layer1.3** `[Observed]` 承擔

**Layer 2 協作表現**
- **C.Layer2** `[Observed]` 專案前/中/後全流程觀察，看一致性

**Layer 3 成長曲線**
- **C.Layer3** `[Observed]` 1-3 個專案週期內必須有可見進步

**特別不能容忍**
- **C.Bad.1** `[Observed]` 不當責 / 不全力以赴 / 動作慢 / 待在 comfort zone
- **C.Bad.2** `[Observed]` 不幫人著想 / 沒 discipline
- **C.Bad.3** `[Observed]` 連續承諾未執行（第三次觸發強情緒）

## D. 組織／規模判準（6 人經驗閾值）
- **D.1** `[Observed]` ≤ 6 人：**穩定優先**（延後汰除、加強支持、避免單點失效）
- **D.2** `[Observed]` ≥ 6 人：**效率優先**（汰除拖累、強化分工、結構性優化）
- **D.3** `[Observed]` 不允許「優化導致崩解」，也不允許「維穩阻礙效率」

## E. 客戶／客製需求判準
- **E.1** `[Observed]` 不允許「繞過系統」的解法（例：非模組客製）
- **E.2** `[Observed]` 標準回覆：「本案採用標準模組配置，不提供客製設計調整」
- **E.3** `[Observed]` 模組內容與組合邏輯由公司決定，客戶只能「選」不可「改」
- **E.4** `[Observed]` 自身教訓：合約交涉太倉促 → 日後損失。**任何被節奏推著走的場景都要慢一拍**

## F. 報價／風險判準
- **F.1** `[Observed]` 報價必須有 **buffer**
- **F.2** `[Observed]` 人際關係必須有 **buffer**
- **F.3** `[Observed]` 寧可慢、不被客戶節奏推走
- **F.4** `[Hypothesis]` 客製需求可分類為：**機會 / 麻煩 / 陷阱**（具體閾值待補訪 → `[Gap]`）

## G. 外部影響／合作判準
- **G.1** `[Observed]` 內部系統優先，不為外部槓桿讓步（除非他親自 override）
- **G.2** `[Observed]` 對外不解釋、不辯論

**G.3 三段標準語**
| 情境 | 親口示範語句 |
|---|---|
| 對方越界 | 「這個部分在我們內部決策範圍，我們會評估後回覆結果。」 |
| 對方持續施壓 | 「我們理解這個方向，但目前不會調整既有決策。」 |
| 已影響團隊 | 「這一塊我們會內部消化，不會直接在團隊中執行。」 |

## H. 必 Escalate 情境（任一觸發 = 直接 Escalate）
- **H.1** 紅線可能被踩（違法 / 欺騙嫌疑 / 重複承諾未執行第三次）
- **H.2** 客戶要求超出標準模組
- **H.3** 報價金額大、buffer 不足、變更風險未涵蓋
- **H.4** 員工自己信心度低
- **H.5** 設計品味爭議（結構 vs 表面）
- **H.6** 任何「看似服務好但可能傷公司長期結構」的決定
- **H.7** 涉及外部夥伴 / 投資人 / A 輪 / SIIR 相關
- **H.8** 模型沒覆蓋的情境（標 Gap）
- **H.9** 兩位總監標準衝突時 `[Gap → Escalate]`
- **H.10** 員工過載時的「放手」決策（涉及 system integrity 時）`[Gap → Escalate]`

## 已知 v0.1 缺口（持續更新，遇到一律 `[Gap]` → Escalate）
1. 報價 buffer 的具體 % 或金額閾值
2. 哪三種員工回覆語句他會打掉重寫
3. 「看似服務好但傷公司」的具體歷史案例 1-3 個
4. 客製需求「機會 / 麻煩 / 陷阱」的具體區分案例
5. Escalate 的金額／風險具體閾值
6. 育如等關鍵員工的「自決 vs 升級」授權邊界
7. 兩位總監標準衝突時的優先順序
8. 員工過載時「放手」與「升級」的選擇規則
9. 補位變成常態時的編制 / buffer 處理規則
10. 員工自信邊界不穩時的授權處理規則
